# Web 开发技术现状与课程思政报告

姓名：甘文韬。课程：软件开发实践 2，下午班第 8 组。

项目：WEMOVE SPORTS 运动产品门户网站。本人职责：组长、架构与工程整合，并承接 B2B 经销商采购模块。日期：2026 年 9 月 8 日。

## 一、从页面开发到完整 Web 系统

在这次实践中，我对 Web 开发的认识逐渐从页面和接口扩展到完整业务系统。WEMOVE 同时包含品牌官网、消费者中心、经销商门户和运营后台。四类用户看到的页面不同，但商品、价格、库存和身份数据需要保持一致。一个按钮能点击，只能说明界面有响应；是否允许当前用户操作、失败时数据是否回滚、重复提交是否产生重复订单，才决定这个功能能否可靠使用。

项目采用 Next.js 和 TypeScript 构建前端，NestJS 组织后端业务，PostgreSQL 与 Prisma 管理数据，Redis 支持缓存和限流。这些工具提供了工程基础，但不能替代业务设计。例如，服务端渲染有助于让公开商品内容被直接访问，交互组件负责表单、购物车等操作；后台仍必须独立校验权限，不能把隐藏菜单当成安全控制。类型检查能发现数据结构不一致，却不能自动判断企业是否有权使用某份价格表。

我在承接经销商模块后，重点处理了企业申请审批、授权目录、快速下单、询报价和采购订单之间的关系。报价需要有版本和有效期，转单需要保存商品与金额快照，库存预留、取消返库和发货需要遵守状态变化规则。这让我理解到，数据库事务、唯一约束和幂等处理并不是抽象知识，而是避免超卖、重复订单和账实不符的具体手段。

## 二、工程协作与验证责任

现代 Web 开发不仅依赖框架，也依赖可复核的协作流程。多人同时修改代码时，各自分支测试通过，并不意味着合并后仍然正确。此次操作手册与主分支整合，也提醒我同时检查代码、文档和实际界面是否一致。作为组长，我需要保留成员已有成果，处理接口边界和集成问题，并对最终组合版本重新验证。

项目通过 GitHub Actions 执行代码检查、构建、单元测试、数据库集成测试和浏览器测试。测试报告必须说明对应提交、测试环境和覆盖范围。浏览器测试通过不能被写成所有真实用户都不会遇到问题，少量并发采样也不能替代一百并发的容量结论。对尚未验证的环境和指标明确留出边界，比写一个缺少依据的“全部完成”更有价值。

在 AI 辅助开发中，我使用大模型帮助梳理需求、排查问题和组织文档，但仍需检查生成代码的权限边界、异常路径和测试结果。AI 可以提高编写速度，不能代替本人承担交付责任。对于团队成果，应区分成员原有工作和后续整合补齐，不能把工具生成的内容或其他成员的实现都写成本人独立完成。

## 三、从两个项目理解数据与用户责任

此前的职位信息分析与推荐项目，使我开始关注数据来源、清洗口径和推荐解释。职位样本只能反映所用数据的情况，不能直接代表整个招聘市场；规则和文本相似度产生的推荐，也不能被描述为已经证明适合每位求职者。这段经历让我意识到，技术展示中的数字和结论会影响用户判断，开发者应说明证据及其限制。

在 WEMOVE 中，同样的责任体现在价格、库存、产品说明和交易记录上。面向儿童运动产品的展示，不应为了营销夸大安全效果；账号和交易面向成年人，也不能把成年人勾选声明写成已经完成真实年龄核验。用户提交的地址、联系方式和企业资质，应只在必要的业务范围内访问。私有资源签名、企业数据隔离、后台多因素认证和审计记录，都是把保护用户落实到代码中的方式。

我对课程思政的理解，是在工程选择中尊重事实、尊重他人权益并承担公共责任。比如保留真实测试失败记录，避免未经授权的数据访问，提供键盘可操作的页面和减少动态效果的设置，都是开发者可以具体做到的事情。可访问性也提醒我，不能只按照自己的设备、视力和操作习惯判断页面是否好用。

## 四、实践总结与后续改进

这次实践锻炼了我从需求理解、模块实现到团队整合的完整工作能力，也暴露了前期接口约定和交付检查不够细的问题。后续我会更早明确验收条件，把权限、错误处理、测试数据和操作说明纳入开发过程，并将课程演示环境与真实生产服务的能力分开说明。

对我而言，完成项目不仅是把功能做出来，还包括让别人能够运行、检查和理解它。能够说明一项功能如何验证、哪些条件尚未满足，并据此继续改进，是这次课程带给我的主要收获。
