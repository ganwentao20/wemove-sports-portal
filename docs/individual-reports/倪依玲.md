## 一、我对当前 Web 开发技术的了解

这门课之前，我对 Web 开发的理解主要停留在网页制作。这次动手开发后，我逐渐理解了前后端的分工：前端负责页面和交互，后端负责数据和业务逻辑，两边通过 HTTP 接口通信。我们使用 Next.js、TypeScript 和 NestJS；我作为组员 D，主要负责运营管理后台（Admin UI）、CMS、媒体中心、联系工单与 SEO，因此实践最多的是 Next.js 页面调用 API，以及按 NestJS 规范组织接口。

后端位于 apps/api，使用 NestJS 12，按 Controller、Service、Prisma 分层组织模块，全局前缀为 /api/v1。写工单、CMS 和媒体接口时可以复用统一结构。class-validator 与 class-transformer 用于 DTO 校验和参数转换，依赖注入便于复用共享服务。当前版本没有配置 Swagger UI，因此 /api/docs 不是可用入口。业务审计通过 AuditService 或业务事务显式写入，请求访问日志由单独中间件记录，两者不能混为一谈。

前台是 apps/web 一个 Next.js 16 应用，通过路由区分四类入口：官网、/customer、/dealer、/admin。我负责的 /admin 后台挂在同一个 Next 应用下，Next.js Route Handler 处理会话 Cookie、CSRF 和受保护请求转发；角色权限及企业数据边界由 NestJS 的守卫和业务服务强制校验，界面依据权限显示入口。SSR/ISR 有助于首屏内容交付与 SEO，项目还通过 metadata、robots、动态 sitemap 和 301 重定向规则完善搜索引擎访问。

数据层是 PostgreSQL 16 + Prisma 6。我在负责的 CMS、媒体与联系工单功能中参与数据模型和迁移的维护。开发环境中用 prisma migrate dev 生成迁移、同步建表；在这个过程中，我体会到字段、约束与数据库版本必须同步，也栽过不少跟头：模型加了字段却没跑迁移、表没更新，查询就报字段不存在；PostgreSQL 对类型和约束更严格，换库后才发现之前含糊过去的地方都行不通。这让我明白：ORM 不是银弹，底层数据库原理还是要懂，否则报错看着唬人，原因其实很朴素。

本地基础设施通过 Docker Compose 编排 PostgreSQL 16、Redis 7 和 Mailpit。按 README 配置环境后，使用 npm ci 安装依赖，npm run db:up 启动基础设施，再执行迁移及所需种子数据，通过 npm run dev 启动 API 与 Web。GitHub Actions 执行依赖安装、Prisma 生成、代码与类型检查、单元及数据库集成测试，并构建 API 和 Web，帮助及早发现问题；具体通过结果以对应提交的 CI 记录为准。CI 里 PostgreSQL 16 和 Redis 7 是真实启动的服务，数据库集成用例会实际连库验证——这套工程化体验，是我写 Python 脚本时完全没有的概念。

安全方面，媒体下载使用 HMAC-SHA256 临时签名。常用授权下载入口默认有效期为 60 秒，具体期限以接口返回为准；后台签发接口可指定有效期，私有文件签名缺失、无效或过期时返回 403。服务端根据资源与到期时间计算签名并进行校验。这直接服务我负责的媒体中心私有附件：经销商资质文件限 PDF/JPG/PNG，单文件不超过 5 MiB。时效签名限制了私有下载链接的有效时间，但链接在有效期内仍可能被重复使用，因此不能将其视为一次性下载令牌。

另外，项目产品面向儿童，账号与交易只面向成年人，注册要求成年人确认。确认字段缺失或类型错误由 DTO 校验拒绝；ageConfirmed 为 false 时由业务层拒绝。当前统一响应使用 HTTP 400 和业务码 42200；这是一项成年人声明，不代表实际年龄已被核验。

## 二、课程思政

我理解的课程思政，需要落实到开发者对用户和数据的责任中。权限隔离防止越权操作，审计日志为问题追溯保留依据，不收集儿童账户信息则减少不必要的隐私风险。这次项目里，我在后台与内容模块中复用并配合完善权限和审计约定，也学习了成年人声明等全站要求。具体措施需要结合业务和实际测试判断，不能仅凭界面提示就宣称系统已经安全或全面合规。

## 三、总结

这门课让我从脚本练习走向后台页面和接口模块开发。我开始学习把代码、迁移和操作说明放在同一个交付过程中检查，也认识到问题定位和团队联调仍需要继续练习。
