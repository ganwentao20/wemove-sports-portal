# Web 开发技术现状与课程思政报告

姓名：周慧莹。课程：软件开发实践 2，下午班第 8 组。

项目：WEMOVE 原网站与业务门户重构。本人职责：组员 C，商品、库存、价格引擎与订单模块。原稿日期：2026 年 9 月 7 日；本稿根据项目整合结果于 2026 年 9 月 8 日校订。

## 一、从项目实践认识 Web 开发技术

WEMOVE 包含品牌官网、消费者中心、经销商门户和运营后台。参与商品与交易域开发后，我认识到，Web 系统不仅要把内容展示出来，还要确保同一商品在不同身份、价格规则和库存状态下得到正确处理。页面、接口和数据库之间的约定，决定了用户看到的信息能否与最终交易结果保持一致。

项目使用 Next.js、React 和 Tailwind CSS 构建前端，以 NestJS 组织后端模块，使用 PostgreSQL 与 Prisma 管理数据。前后端采用 TypeScript，有助于尽早发现参数类型和数据结构不一致的问题；但类型正确不代表业务正确，运行时仍需验证数量范围、商品状态和用户权限。服务端渲染、缓存与交互组件各有适用场景，性能效果需要结合页面和部署环境测量，不能仅凭采用某个框架就认定系统足够快。

后端模块化设计使价格、购物车、订单等职责较易区分。数据库迁移、外键和唯一约束帮助维护数据关系，事务则用于保证多项写操作共同成功或共同回滚。Prisma 提高了查询和迁移的编写效率，但我仍需要理解 SQL 的条件更新与行锁，才能判断并发结算是否存在重复下单或库存不足的问题。

工程质量同样属于 Web 开发的一部分。仓库通过统一脚本执行代码检查、类型检查、测试和构建，CI 还单独运行数据库集成测试和浏览器测试。Redis、邮件服务、审计日志和多因素认证由团队协同实现，我需要理解其接口与限制，也应如实区分个人负责的工作和其他成员提供的能力。AI 可以辅助解释概念、排查错误和整理文档，生成的实现与结论仍需要本人理解并验证。

## 二、商品与交易域的实践工作

### 价格规则与权限边界

我在 C1 工作中处理了价格规则管理与价格引擎装配。经销商价格按照企业专属价、价格表价、等级价、B2B 默认价的顺序选择；在适用范围内，按购买数量选择满足条件的最大起订量档位，同档位再比较规则优先级。这表达了阶梯定价的选择规则，但是否“买得越多单价越低”仍取决于配置，不能由算法自动保证。

规则计算与数据库查询分开，使价格逻辑可以用明确的规则和上下文测试。当前实现还需要考虑市场、币种和有效期；测试涉及时间边界时，应显式传入时间，避免结果随运行时刻变化。零售价和经销商价采用不同的取价入口，零售价按有效促销价优先、标价兜底处理。

价格计算不能代替授权。企业专属规则必须匹配当前企业，价格表需要属于企业获授权的集合。仅有非空的 companyId 不能证明企业已获批准或用户有权访问；服务层仍须检查登录身份、有效成员关系和企业状态。价格规则后台也要校验操作权限、敏感写操作的多因素认证，以及 SKU、价目表等引用是否有效，并保留审计记录。评审中暴露的用户归属、规则引用和测试缺口，使我认识到功能完成前还需要检查异常输入与越权路径。

### 购物车、订单与库存一致性

在 C2 购物车工作中，我按 SKU 管理购物车行，同一购物车内同一 SKU 通过唯一约束避免重复行，再由服务层合并数量。查询和修改必须限定到当前用户，不能因为请求提供了购物车行 ID 就允许操作。商品被禁用后，也要重新检查其是否仍允许购买。

购物车保存价格快照便于展示，但该快照不是最终成交价承诺。当前整合实现会在结算时重新校验商品、库存与服务器价格，并将成交金额写入订单快照。订单创建后保存的商品名称、SKU、单价和小计，用于说明当时的交易结果，不能随商品资料后续修改而重算。

围绕结算与库存，我重点理解并复核了三类约束：同一购物车的并发结算需要串行处理；库存预留必须使用带“可用数量足够”条件的原子更新；订单和库存的多项变化应放在同一事务中，任一步失败就回滚。预留是将库存从可用量转入保留量，取消和发货还须按相应状态处理。金额使用整数最小货币单位，并校验安全整数及数据库整数范围，避免溢出。

订单履约状态与支付状态也不能混用。当前系统在确认、取消、发货和售后环节分别检查业务条件，已支付订单的退款不能被简化成直接修改取消状态。早期基础订单状态机只是其中一部分，团队后续整合的支付、履约和售后能力应按最终代码与测试报告说明。

### 数据字典与交付记录

我提交的数据字典 v1.0 记录了当时商品、价格、购物车和订单核心模型的字段、约束及业务含义，并提出 11 项改进建议。复核原稿后，模型计数应为 10 个，包含 ProductCategory；原个人报告中的“9 个”遗漏了该模型。价格有效期、支付状态与引用约束等建议对应当时版本，不能直接作为当前项目的未完成项。

## 三、协作、排障与验证责任

实践中，我遇到过 Docker 无法启动、数据库认证失败和 GitHub 连接中断。通过改用本机 PostgreSQL、核对连接配置、调整网络连接方式等操作逐项排查，我体会到环境问题需要根据具体错误定位。可以将处理经验整理给队友参考，但不能把某台电脑的排障办法写成适用于所有环境的固定结论，也不应在文档中暴露真实连接凭据。

合并代码时，购物车模块与经销商模块曾在共同的入口文件中产生冲突。解决方式是理解两侧改动并保留各自需要的模块注册，再验证组合后的行为。共享数据库结构变更也需要与相关成员说明影响，补齐迁移和接口文档，避免一方改完后让另一方承担未说明的兼容问题。

测试结论应对应实际版本和环境。原稿中的 CI #40 与早期测试数量属于阶段记录，不能用来证明最终组合版本已经验证。团队测试报告保留了 CI #54 对应提交 f3c074f 的 110 项单元测试、169 项数据库集成测试及合计 70 项浏览器与性能检查记录，并单独说明 CI #51 的性能样本。具体范围与限制以[当前测试报告](../test-report.md)为准，这些是团队验证结果，不等于我的个人测试数量，也不能推导为所有线上场景均已覆盖。

## 四、课程思政认识与体会

商品和交易数据关系到用户的实际权益。把金额单位、价格来源、库存条件和失败回滚写清楚，是严谨工作的具体要求。我对精益求精的理解，不是无限增加复杂设计，而是在关键边界上给出可验证的处理，使错误输入和并发请求也能得到合理结果。

保护用户数据需要落实到每次访问。购物车、订单、企业资质等数据应限定到有权访问的人；公开接口不应返回内部草稿或敏感字段。HttpOnly Cookie 可以限制脚本直接读取会话 Cookie，但并不能消除所有脚本攻击；私有媒体的短时签名同样需要先做业务授权。当前服务默认签名期限为 60 秒，具体以接口返回为准，不能把最长允许期限写成所有资源固定有效 5 分钟。

诚信也体现在交付表述中。评审发现问题后，需要承认并修复；尚未验证的指标需要说明限制；成员分工、个人贡献和团队整合结果应分开记录。使用 AI 后更要检查细节，避免把看似合理的解释当作已有代码事实。测试通过只说明相关用例在指定环境下得到预期结果，不能为了材料完整而补造未运行的数据。

团队协作使我进一步理解个人责任与共同成果的关系。价格和购物车接口既服务消费者页面，也影响经销商模块及测试工作。清楚说明参数、错误码和数据归属，有助于其他成员减少误解。主动补位与尊重他人成果可以同时做到，最终交付应保留真实来源，让每位成员的工作都能够被核对。

## 五、不足与后续改进

我对 Redis 缓存与降级策略的理解仍以学习和接口配合为主，对 Next.js 缓存、流式渲染等细节也需要继续实践。性能验证方面，我参与的早期工作偏向只读请求，对混合读写负载和长时间稳定性测试的独立经验不足。后续需要通过可复现的小型实验理解瓶颈，而不是仅记住某次压测数字。

提交前的自查也应更完整。我会在常规功能之外增加权限归属、引用有效性、数值边界、时间条件和重复请求的检查，并及时同步文档。此次实践让我认识到，可靠的 Web 开发需要把技术实现、团队协作和事实表达共同做好，才能让其他人依据材料理解、运行和检查系统。
