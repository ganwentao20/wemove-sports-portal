## 一、项目背景与本人任务

### （一）项目背景

WEMOVE SPORTS 项目面向运动游戏玩具品牌官网重构，业务对象包括普通游客、注册用户、经销商以及内部运营人员。系统并非单纯的宣传主页，而是要求逐步形成品牌官网、用户中心、经销商门户和运营管理后台相互协作的综合平台。产品、内容、用户、经销商、价格及订单等核心数据由不同模块维护，并通过统一的接口完成前后端协作。

### （二）本人任务

根据小组分工，我主要负责前端部分。具体来说，我完成了网站的响应式布局和公共区域，如导航栏、公告条和页脚；参与首页的展示内容；负责产品列表、产品详情和产品对比页面；同时完成 B2C 用户中心中的注册、登录、找回密码、个人资料、地址簿和收藏夹等页面与交互。我也参与了小组沟通记录的整理。

在实际开发中，我越来越明显地感受到，前端并不是独立完成页面就可以。很多功能都要依赖后端接口，测试也需要前端提供稳定、可以验证的流程。只有大家把职责、接口和版本说明清楚，项目才能顺利推进。

项目采用 Next.js 与 TypeScript 组织前端页面，通过接口与 NestJS 后端协作，PostgreSQL、Redis 和 Prisma 分别承担数据存储、缓存及模型迁移工作。组件化便于复用公共界面，类型约束和接口契约帮助多人保持一致；实际性能与安全仍需通过运行和测试确认，不能仅凭选用了某个框架判断质量。

## 二、项目实践中的主要收获

### （一）项目过程中思路的改变

项目前期我先追求的是每个页面的框架有没有建好，但随着需求拆分和验收项增加，我逐渐发现页面框架只是第一步。例如产品列表购买流程的真正完成需要筛选、排序、空状态、收藏、比较和跳转；产品详情除了主图与文案，还需要规格、卖点、玩法、安全说明等信息；用户中心也不仅是登录页，还包括资料、地址和收藏的连续流程。通过逐步完善这些交互细节，我对网站重构中的前端职责有了更具体的理解。

### （二）GitHub合作遇到的问题

这是我第一次使用 GitHub 参与多人开发。起初我不熟悉分支协作，只顾修改自己的分支，忽略了同步和合并主分支，后来遇到了个人分支同时领先、又落后于 main 的情况。处理这些问题后，我开始理解 GitHub 在团队版本管理中的作用。及时同步主分支、写清楚提交说明、通过 Pull Request 合并，以及遇到冲突时判断应该保留哪部分代码，都是我需要养成的习惯。

## 三、课程思政体会

通过这次开发，我明白前端页面能显示出来只是开始，按钮反馈是否清楚、页面跳转是否合理、不同尺寸下布局是否正常，这些小细节都会影响真实用户。以前我更关注“能不能做出来”，现在会更在意“能不能做好、用起来顺不顺”。

同时，我也更理解团队协作的重要性。前端、后端、CMS、经销商模块和测试之间互相依赖，一个人的代码只有真正接入整个系统后才有价值。主动沟通接口、同步分支、记录问题和说明未完成内容，看起来不是写代码本身，但这些事情会直接影响整个小组的效率。

项目还让我意识到，Web 开发必须重视规则、隐私和数据安全。系统会处理账号、地址、订单、价格等信息，所以不同用户应该有不同权限，例如普通用户不应该看到经销商专属价格，后台功能也应该按照角色进行限制。涉及用户信息时，也应尽量少收集不必要的数据，并注意表单、账户和日志中的安全问题。

这些问题让我明白，技术不是只要“能实现”就可以，开发者还要考虑功能是否合理、是否会影响用户权益。遵守规则、保护数据、避免滥用技术，也是软件开发中很重要的责任。

因为这个项目面向家庭用户、消费者和经销商，而且产品与儿童运动有关，所以页面设计还要考虑真实用户的感受。比如保护隐私、让操作步骤清楚、让用户知道自己提交了什么信息以及下一步会发生什么。

## 四、存在的不足与改进方向

通过这次项目，我也看到了自己的不足。现在我对复杂前端功能的整体规划还不够成熟，GitHub 多人协作中的分支同步和冲突处理也需要继续练习；在后端接口未完成时，mock 数据与正式接口的切换也可以更规范。以后我会先整理需求清单，以功能是否完整作为进度标准，并养成及时同步 main、提前和后端沟通数据结构与错误状态的习惯，让自己的开发过程更有条理，也更适合团队协作。
